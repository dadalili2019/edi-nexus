# ADR-0001：文档优先与持续记录

- 状态：已确认
- 日期：2026-10-10
- 适用项目：EDI Nexus

## 背景

EDI Nexus 会经历较长时间的功能设计、架构设计、技术选型、开发、测试和 Kubernetes 集群验证。

如果设计只存在于聊天记录中，会出现几个问题：

- 隔一段时间后难以恢复上下文
- 不知道某个设计为什么这样决定
- AI / Codex 可能只看到局部信息
- 文档和实际讨论逐渐脱节
- 项目设计者自己也难以持续维护整套思路

## 决定

EDI Nexus 采用“文档优先 + 持续更新”的方式。

每次重要讨论形成结论后：

1. 更新对应专题文档
2. 更新相关架构图
3. 回写总体设计
4. 更新当前设计上下文
5. 记录未决问题
6. 重要架构决定新增或更新 ADR

## 文档第一读者

第一读者：

**项目设计者本人。**

第二读者：

- 开发人员
- AI
- Codex

因此文档必须先保证人容易理解，再保证机器容易恢复上下文。

## 图文原则

重要设计采用：

> 中文说明 + Mermaid 图

图用于快速理解关系，文字用于解释“为什么”。

## 为什么不只依赖聊天记录

聊天记录适合探索过程，不适合作为最终项目知识库。

Git 仓库中的 Markdown 文档可以：

- 版本化
- 对比变化
- 和代码一起维护
- 被开发人员阅读
- 被 AI / Codex 重新读取

## 后续影响

以后每个阶段完成后，都必须把最终结论沉淀回仓库。

即使还没有开始写业务代码，仓库也已经是项目正式知识库，而不是一个空代码仓库。
